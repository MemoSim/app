01 / THE WORKFLOW

Make the conversation
do the modeling work.

Start in the assistant panel. Describe the system, then refine one idea at a time. The desktop model is the thing you inspect, test and save.

01

Frame the question

Name the agents or stocks, the rules, the time unit and the measure that would answer your question. State your assumptions.

02

Create a small base

Ask for a minimal model with setup, a bounded run and visible measurements. Review the proposed tool actions and compiler feedback.

03

Extend with intention

Ask for one change: a slider, a plot, a new behavior or a feature. Run the base checks again after each change.

04

Compare, then share

Vary one input, repeat across seeds and compare results. Save the native model and document the environment before deployment or sharing.

Read the evidence, not just the answer.

A successful chat response is not proof that a model is correct. Inspect tool results, check assumptions, run the model and validate its outputs. Cloud chat still needs its configured service; this manual itself works offline.

01

The plan card

A turn that needs design work proposes a plan: what it understood, how the model represents the phenomenon, the agents, the rules, the measured outputs, the levers, the assumptions. Approve it, or correct it in your own words; the assistant re-plans instead of building the wrong model.

02

One work log per turn

While the assistant works, a single line reports the live phase, the elapsed time and the number of actions taken. Expand it to see every tool call in order with its duration, the code diff it applied, and any notice.

03

The approved model is pinned

Defining an experiment locks the model: edits are refused until the run finishes, and a run is refused if the model changed after the experiment was defined. Press Unlock in the header when the model itself must change.

04

Failures are named

Connection problems are reported by cause: a rejected key, a wrong URL, a rate limit, a context overflow, a provider stall. Connection diagnostics in the header shows the model, the endpoint, a live latency test and the recent events.

Plan confirmation can be set per workspace: auto (new models and structural changes), always, or off.
